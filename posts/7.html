用 uv 搞定 Python 多环境：一个工具替代 venv、pip 和 Poetry

技术 2026-11-11
Pythonuv环境配置虚拟环境

如果你还在用 venv 建环境、pip 装包、poetry 管依赖，那一定体会过它们各自的摩擦：pip 慢、poetry 重、Python 版本还得靠 pyenv 额外管理。最近两年，uv 这类一体化工具把这些事一把梭了。本文用 uv 为主线，讲清楚怎么用它做 Python 的多环境配置。

1. 为什么是 uv

uv 是 Astral（也就是做 ruff 的那家公司）用 Rust 写的 Python 包与环境管理器，极快，且一个工具替代 venv、pip、pip-tools、poetry、pyenv：建环境、装依赖、锁版本、切 Python 版本，全包了。

# 安装 uv
pip install uv
# 或官方脚本
curl -LsSf https://astral.sh/uv/install.sh | sh

2. 一条命令建环境

uv 内置虚拟环境管理，还能自动下载指定版本的 Python，不再需要单独装 pyenv：

# 创建虚拟环境（自动使用项目声明的 Python 版本）
uv venv

# 需要特定版本？uv 会自己下载
uv python install 3.12
uv venv --python 3.12

3. 依赖管理：uv add 与 uv.lock

uv 采用项目模式，依赖写在 pyproject.toml，并生成锁定文件 uv.lock 冻结整棵依赖树，保证所有人装到一模一样的版本：

# 初始化项目并添加依赖
uv init myproject
cd myproject
uv add requests flask

# 按锁定文件安装全部依赖（CI / 生产常用）
uv sync

相比手写 requirements.txt，uv.lock 不用你手动固定每一个间接依赖，既省心又可靠。

4. 跑起来：uv run

不用手动 activate，直接用 uv run 在受管环境里执行命令：

uv run python main.py
uv run pytest

5. 多环境配置：用 .env 分离配置

依赖解决了，配置呢？数据库地址、密钥等仍然不能写死在代码里。uv run 会自动加载项目根目录的 .env，也可以用 --env-file 指定不同环境的文件：

# .env.prod
DATABASE_URL=postgresql://user:pass@db/prod
DEBUG=false

# 用生产配置运行
uv run --env-file .env.prod python main.py

代码中照常通过环境变量读取：

import os
db_url = os.environ.get("DATABASE_URL")
debug = os.environ.get("DEBUG") == "true"

6. 一套代码，三套环境落地

把依赖与配置按环境分开，目录可以长这样：

myproject/
├── .env.dev        # 开发配置
├── .env.prod       # 生产配置
├── pyproject.toml  # uv 管理依赖
├── uv.lock         # 锁定全部依赖
├── src/
└── tests/

推荐流程：本地 uv venv + uv add 开发，提交 uv.lock；CI 用测试配置跑 uv run pytest；生产用 uv sync --frozen 安装锁定版本，并通过 --env-file .env.prod 或注入环境变量加载生产配置。

7. 与十二要素（12-Factor）的关系

业界 12-Factor App 主张「配置来自环境变量」。uv 的 --env-file 与自动加载 .env 正好契合这一点：同一份构建产物，靠环境变量切换 dev / test / prod，是 CI/CD 和多环境部署的基石。

结语

用 uv 做多环境配置，核心就三步：uv venv 隔离依赖、uv.lock 锁定版本、.env + uv run --env-file 分离配置。一个工具顶替过去四五个，速度快、心智负担小。把这套流程建立起来，多环境部署会顺滑很多。
