Python 装饰器深入：从闭包与描述符到生产级模式

技术 2026-11-11
Python装饰器闭包functools元编程进阶

@decorator 大概是 Python 里最容易被「会用但说不清」的特性。多数教程停在「接收函数、返回函数」就结束了，可一到真实工程就会撞上：装饰后函数签名变了、装饰类方法报 TypeError、异步协程被包装成协程对象却没被 await、多个装饰器的顺序和想象的不一样。这篇从运行机制往下挖，把这些坑一次说透。

一、装饰器到底是什么

先确立三个前提：

  1. 函数是一等对象：可赋值、可传参、可作为返回值，def 只是把一个函数对象绑定到名字上；
  2. 闭包：内层函数引用了外层的自由变量，Python 会把它装进 __closure__ 的 cell 里长期保留；
  3. 装饰器是调用表达式：@d 不是语法魔法，它等价于在函数定义之后立刻执行 f = d(f)。
@timer
def work(): ...

# 完全等价于：
def work(): ...
work = timer(work)

由此立刻得到两个常被忽略的结论：装饰器在模块导入时执行一次（不是每次调用），且它永久替换了名字所指向的对象。所以装饰器里的顶层逻辑只跑一次，而包装函数里的逻辑才每次调用都跑。

def show_closure(fn):
    def wrapper(*args, **kwargs):
        return fn(*args, **kwargs)
    print(wrapper.__closure__)        # (<cell: function show_closure.<locals>...>,)
    return wrapper

二、第一个正确的装饰器：*args 与 wraps

import functools, time

def timer(fn):
    @functools.wraps(fn)                      # 关键，见下
    def wrapper(*args, **kwargs):            # 透传任意签名
        t0 = time.perf_counter()
        try:
            return fn(*args, **kwargs)       # 别忘了 return
        finally:
            print(f"{fn.__name__} took {time.perf_counter()-t0:.3f}s")
    return wrapper

@timer
def fetch(url, timeout=3):
    """拉取数据"""
    ...

functools.wraps 用 update_wrapper 把原函数的 __module__、__name__、__qualname__、__doc__、__annotations__ 和 __dict__ 拷到包装函数上，并设置 __wrapped__ 指向原函数。它解决的不只是「名字好看」：

不写 wraps 会坏什么原因
日志 / 文档 / help() 全显示 wrapper元信息被覆盖
inspect.signature(fetch) 变成 (*args, **kwargs)标准库会沿 __wrapped__ 链回溯，没设就只能看包装层
Web 框架自动注入参数失效FastAPI / Flask / pytest 靠签名判断该传什么
无法拿到原始函数做测试或绕过fetch.__wrapped__ 就没了
多个装饰器叠加时调试困难traceback 里全是 wrapper

另外注意 finally 里的计时：即使被装饰函数抛异常也要记录耗时且不能吞掉异常。很多计时装饰器在出错时静默返回 None，是生产事故常见来源。

三、带参数的装饰器：为什么是三层

def retry(times=3, delay=0.1, exceptions=(Exception,)):   # ① 参数层：调用时立即执行
    def decorator(fn):                                     # ② 装饰层：接收被装饰函数
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):                      # ③ 包装层：每次调用执行
            for i in range(times):
                try:
                    return fn(*args, **kwargs)
                except exceptions:
                    if i == times - 1:
                        raise
                    time.sleep(delay * 2 ** i)             # 指数退避
        return wrapper
    return decorator

@retry(times=5, delay=0.2, exceptions=(ConnectionError,))
def call_api(): ...

@retry(times=5) 先调用 retry(...) 得到真正的装饰器，再拿它去装饰函数——这就是多出一层的原因。理解了这点，就能写出「既支持 @log 又支持 @log(level=...)」的可选参数形式：

def log(_fn=None, *, level="INFO"):
    def decorate(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            print(f"[{level}] {fn.__name__}")
            return fn(*args, **kwargs)
        return wrapper
    return decorate(_fn) if _fn else decorate

@log                 # _fn 是函数，直接 decorate
def a(): ...
@log(level="DEBUG")  # _fn 为 None，返回 decorate
def b(): ...

也可以用 functools.partial 把三层写成两层，可读性各有取舍。生产代码里更推荐明确的三层，或引入 decorator / wrapt 库来保住签名。

四、类装饰器与描述符

能被调用的对象都能当装饰器，所以实现了 __call__ 的实例也可以。类装饰器适合需要跨调用保存状态的场景：

class CountCalls:
    def __init__(self, fn):
        functools.update_wrapper(self, fn)
        self.fn = fn
        self.n = 0
    def __call__(self, *args, **kwargs):
        self.n += 1
        return self.fn(*args, **kwargs)

@CountCalls
def work(): ...
work.n          # 可读的计数

但要注意：用类实例装饰实例方法时，描述符协议会失效。普通函数是描述符，访问 obj.method 时会自动绑定 self；而自定义类实例默认不实现 __get__，于是 self 不会被传入，报 TypeError: missing 1 required positional argument。修法是给类补一个 __get__ 返回 types.MethodType(self, instance, owner)。这也是「装饰实例方法优先用函数闭包」的 practical 理由。

装饰器还能直接作用于类本身（接收类、返回类），典型如 @dataclass——它读 __annotations__ 并生成 __init__/__repr__ 后返回同一个类对象。这与 classmethod/staticmethod/property 这些「返回描述符对象」的装饰器属于不同模式。

六、生产级模式

1. 权限校验与横切关注点

def requires_role(role):
    def deco(fn):
        @functools.wraps(fn)
        def wrapper(user, *args, **kwargs):
            if role not in user.roles:
                raise PermissionError(role)
            return fn(user, *args, **kwargs)
        return wrapper
    return deco

装饰器最适合承载这类与业务逻辑正交的横切逻辑：鉴权、日志、埋点、事务、限流。判断标准很简单——把这段逻辑删掉，业务函数的语义是否不变？如果不变，就适合抽成装饰器。

2. 注册器（插件系统）

REGISTRY = {}
def register(name):
    def deco(cls):
        REGISTRY[name] = cls
        return cls          # 返回原类，不包装
    return deco

@register("json")
class JsonExporter: ...

这里装饰器只做注册、返回原对象，是「副作用型」装饰器，没有包装层开销。Web 框架的路由 @app.route、测试框架的标记，本质都是这个模式。

3. 异步协程必须用 async 包装

def async_timer(fn):
    @functools.wraps(fn)
    async def wrapper(*args, **kwargs):        # 必须是 async def
        t0 = time.perf_counter()
        try:
            return await fn(*args, **kwargs)   # 必须 await
        finally:
            print(time.perf_counter() - t0)
    return wrapper

用普通 def wrapper 返回 fn(...) 的协程对象，调用方拿到的是未被 await 的 coroutine，会静默不执行并触发 RuntimeWarning: coroutine was never awaited。若装饰器要同时兼容同步与异步函数，可用 inspect.iscoroutinefunction 分支，或让包装层始终返回可等待对象再判断。

八、什么时候不该用装饰器

  • 逻辑与业务强耦合、需要读大量上下文才能理解时——显式调用比隐式包装更好维护；
  • 需要频繁按条件开关、且开关来自运行时配置时——装饰器在导入期就固定了，改配置不会重新装饰；
  • 团队里多数人不熟悉元编程时，一个 with 或一行显式调用更不容易踩坑；
  • 热路径上层层包装、又拿不出可观测收益时。

装饰器本质上只是「把一个可调用对象替换成另一个」。理解闭包怎么捕获自由变量、wraps 怎么串起 __wrapped__ 链、描述符怎么绑定 self，剩下的所有高级用法都是这三件事的组合。
